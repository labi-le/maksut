# Media downloading, transcoding, delivery, and caching

> **When to read this:** Read before touching URL extraction (`src/links.rs`), video/photo download (`src/download.rs`, `src/download_videos.rs`, `src/youtube.rs`, `src/images.rs`, `src/image_fetch.rs`, `tools/twitter_images.py`), `ffmpeg`/`ffprobe` checks (`src/video_convert.rs`), album delivery and captions (`src/delivery.rs`, `src/caption.rs`, `src/source_message.rs`), the 24-hour `file_id` cache (`src/media_cache.rs`), or download error mapping (`src/diagnostics.rs`, `src/user_errors.rs`).

## Supported sources and short-link resolution

`src/links.rs` accepts single-post URLs from YouTube (`watch?v=`, `playlist?list=`, `/shorts/`, `/live/`, `/embed/`, `/clip/`, `youtu.be`), Pinterest (`/pin/<id>`, `pin.it`), X/Twitter (`/status/<id>`), Instagram (`/p/`, `/reel/`, `/reels/`, `/tv/`), and TikTok (`/@user/video/<id>`, `/@user/photo/<id>`, `/v/`, `/t/`, `vm.tiktok.com`, `vt.tiktok.com`).

- **Short links (`pin.it`, `vm.tiktok.com`, `vt.tiktok.com`).** `yt-dlp` has no extractors for these hosts and `--ies default,-generic` is enforced in `/etc/yt-dlp.conf`. `resolve_short_link` resolves up to 5 HTTPS hops through `pinned_client` before any downloader or cache check runs.
- **TikTok quirks.** TikTok serves a "Site Maintenance" stub to Chrome-like User-Agents from this network, so `TIKTOK_USER_AGENT` sends Firefox (`rv:147.0`). H.264 is sorted ahead of resolution (`-S vcodec:h264,res`) because TikTok HEVC (`bytevc1`) variants are rejected by Telegram inline playback or omit the audio track even when metadata reports AAC.
- **TikTok photo posts (`/@user/photo/<id>`).** Handled outside `yt-dlp` ([ADR 001](../adr/001-tiktok-photos-and-failures.md)): the bot fetches `www.tiktok.com` (passing TikTok cookies only to the page request, never to the CDN), reads `webapp.video-detail.itemInfo.itemStruct.imagePost`, and downloads up to `media.max_tiktok_photos` (default 35) images from signed `*.tiktokcdn*.com` URLs, falling back to alternate CDN URLs in `urlList` when the primary fails.
- **X/Twitter photos (`tools/twitter_images.py`, [ADR 004](../adr/004-photo-classification-and-sender-name.md)).** Extracted in a single walk over direct/legacy/quoted/unified-card media via `yt-dlp`'s `TwitterIE` (`yt-dlp[default,curl-cffi]==2026.7.4`), returning deduplicated `pbs.twimg.com/media/` URLs, post description, and an explicit boolean `has_video` (`video` / `animated_gif` -> `true`) so photo-only posts never trigger a false video failure.

## Audio requirement, YouTube pre-probe, and transcoding

- **Mandatory audio track for video.** Video format selection uses `bv+ba/b[acodec!=none]/ba`. Before sending any MP4 or converting another video container, `ffprobe` verifies that an audio stream exists (`src/video_convert.rs`). A video without audio (or with a failed `ffprobe` check) is neither sent as video nor as a document, and the source link message is kept. Standalone audio files remain supported.
- **Single-video YouTube pre-probe (`src/youtube.rs`).** For a single YouTube video (not a playlist or a URL carrying `list=`), the bot runs a metadata probe (`media.youtube_probe_timeout_secs`, default 25 s, `media.max_metadata_bytes` default 4 MiB). When exact stream sizes are known and their sum plus `media.mp4_mux_headroom` (default 64 KiB) fits `media.max_bytes`, it selects the highest resolution/fps H.264 + AAC pair (or ready MP4 with those codecs) and muxes without re-encoding. Live and upcoming streams or videos over `media.max_video_duration_secs` (default 1800 seconds, 30 minutes) are rejected before media streams open (`--match-filter "!is_live & duration <= 1800"`).
- **Transcoding (`src/video_convert.rs`).** Containers with a moving video stream (`WebM`, `MKV`, `MOV`, `AVI`, `M4V`, `3GP`) are transcoded to MP4 (`H.264/yuv420p` + `AAC`). Cover-art-only streams are rejected. Input dimensions are capped at `media.max_video_dimension` (default 3840) per side and `media.max_video_pixels` (default 3840 * 2160, `8,294,400` pixels); output is scaled down to at most `1920` per side without upscaling smaller videos, and odd dimensions are padded to even numbers for `yuv420p`.

## Delivery, albums, captions, and source deletion

- **Concurrency and limits (`src/main.rs`, `src/settings.rs`).** Downloads run concurrently up to `media.concurrent_downloads` (default 2), with at most `media.user_download_limit` (default 3) active/queued downloads per user. The per-file limit is `media.max_bytes` (default 45 MiB), which validation keeps between 1 and `telegram.file_limit_bytes` (default 50,000,000). Up to `media.max_files` (default 10) files are processed per link, and `media.max_tiktok_photos` (default 35) for TikTok photo posts. After `/maksut off` in a group, queued downloads waiting for a slot abort once they acquire the permit; in-flight downloads finish.
- **Albums and ordering (`src/delivery.rs`, [ADR 006](../adr/006-albums-errors-cache.md), [ADR 009](../adr/009-album-caption-dedupe.md)).** Prepared files preserve post order and group adjacent compatible items into albums of 2 to 10 (`sendMediaGroup`): photos and videos mix together, audio groups only with audio, documents only with documents. Within each album, if multiple items produce the exact same caption (for example, a captionless photo post where every item only has `От ...` and `Ссылка`), the caption is attached only to the first such item; distinct captions stay on their items.
- **No album retry (`src/delivery.rs`).** On an album error or timeout (`telegram.request_timeout_secs` default 180, with `telegram.pool_idle_timeout_secs` default 15 and `telegram.tcp_keepalive_secs` default 15 on the Bot API client), the bot never retries items individually because Telegram may already have accepted part of the group. Single-item photo/audio upload falls back to sending as a document only on an explicit Telegram rejection, never on a network error or timeout.
- **Captions and silent send (`src/caption.rs`, [ADR 003](../adr/003-source-post-media-captions.md), [ADR 005](../adr/005-silent-nonmention-replies.md)).** Every outgoing message sets `disable_notification = true`. Captions start with the post title, then a blank line and description (deduplicated if identical or if the title is a truncated prefix of the description; generic titles like `Video by ...`, `Photo by ...`, `<source> video #<id>` are stripped), followed on separate lines by HTML-escaped `<code>От first_name</code>` (never `@username`, so the sender is not pinged) and clickable `<a href="...">Ссылка</a>`, truncated to 1024 UTF-16 code units.
- **Source message deletion (`src/source_message.rs`).** The original message containing the link is deleted only when every supported item was delivered without skips or unsupported files (such as `.flv`). If deletion fails in a group because the bot lacks `can_delete_messages`, the bot sends a warning naming the required admin permission.

## 24-hour `file_id` cache (`src/media_cache.rs`, [ADR 006](../adr/006-albums-errors-cache.md))

- **Key and scope.** Keyed by SHA-256 of `(bot_token, chat_id, normalized_url_with_query)`. Different chats, different query strings, or a changed bot token never share cache entries. Raw URLs, queries, and tokens are not stored in plaintext in the key column.
- **Write conditions.** Stored only after a complete, skip-free delivery where Telegram returned valid `file_id`s for every item (failed deletion of the user's source message does not block caching).
- **Retention and invalidation.** Entries expire 24 hours after the fresh download (cache hits do not extend TTL) and are capped at the 200 newest rows globally across all chats. If Telegram explicitly rejects a cached `file_id` before any item of that request is delivered, the bot invalidates the row and performs one fresh download; after partial delivery, `429`, network error, or timeout, it does not retry.

## Error classification and diagnostics (`src/diagnostics.rs`, `src/user_errors.rs`)

- **Safe, detailed categories.** Source errors include the human-readable limit (`media.max_bytes` in MiB, `media.max_video_duration_secs` in minutes, `media.max_files`) and distinguish HTTP `403`, `404`, private/unavailable post, authentication required / expired cookies, geo-restriction, age/NSFW restriction, live stream, duration cap, format/codec mismatch, HTTP `429`, HTTP `5xx`, timeout, single-file size limit, temporary storage limit, unsupported URL/extractor, and missing metadata/media. Delivery errors distinguish Telegram `429` (with `retry_after` when present), file too large, bot blocked/kicked/missing rights, message thread not found, invalid `file_id`, network/timeout, and I/O error. When multiple diagnostic stages are recorded (such as a cookie refresh retry), the user message appends a safe ordered trace chain (`цепочка: ...`).
- **SQLite failure journal.** `download_failures` (parent row: UTC timestamp, `url_host`, `url_path` without query, initial `stage`, `detail`, `exit_code`, capped at 200 rows) and `download_failure_events` (up to 12 ordered trace steps per failure: initial attempt, cookie refresh request/confirmation, retry, delivery). After a cookie refresh or fallback attempt, `source_user_diagnostic` surfaces the last substantive cause to the user while keeping the initial auth failure in the parent row.
